\begin{abstract}
Large language model (LLM) agents have shown strong capabilities on complex tasks, encouraging multi-agent systems that coordinate specialized roles. Improving how these agents collaborate requires flexibility, so that coordination decisions are still made at runtime, together with controllability, so that they can be inspected and revised afterwards. Existing systems supply only one of the two, because a predefined workflow fixes the execution route while free-form communication leaves the realized coordination opaque. In this paper, we introduce OpenAgency, a self-evolving multi-agent system built on governed collaboration protocols. A protocol defines roles, admissible handoffs, handoff modes, and completion conditions, and each agent still selects its next collaborator inside the admissible set, which turns the collaboration pattern itself into an evolvable object. To evolve that object, OpenAgency keeps an immutable trace that retains rejected handoffs and failed completions alongside successful events, and a collaboration-driven evolver converts this evidence into a bounded number of atomic protocol edits, each filtered by a validity operator and accepted only without regression on a held-out subset. Experiments on fourteen benchmarks show that OpenAgency achieves the best primary metric on every benchmark, covering general question answering, long-horizon tasks, and production-oriented tasks. These results show that a governed protocol is an effective object for multi-agent adaptation.
\end{abstract}


\section{Introduction}

Large language models (LLMs)~\citep{gpt4,chatgpt} have shown strong capabilities on complex tasks such as software engineering~\citep{yang2024sweagent,wang2024openhands,zhang2024autocoderover}, data research~\citep{liu2026ddrbench,li2024deveval}, and long-horizon planning~\citep{zhang2026deepplanning,xu2024theagentcompany}. Multi-agent systems built on LLMs extend these capabilities by assigning complementary roles that exchange intermediate evidence~\citep{wang2024survey,xi2023rise,hong2024metagptmetaprogrammingmultiagent,qian2024chatdevcommunicativeagentssoftware,wu2023autogenenablingnextgenllm}, which lets one system plan and verify the same task through cooperation. However, as tasks become longer and more heterogeneous, the collaboration process itself becomes both a source of errors and an underused source of improvement.

Evolving the way agents collaborate requires flexibility and controllability at the same time. Flexibility matters because a multi-agent system, unlike a single agent that revises its own reasoning inside one context, must recover what went wrong across roles, and a system that cannot repair a failed handoff at runtime loses the remainder of the run along with it. Controllability is equally necessary, since an update is informative only when the system can tell which coordination step was responsible and can verify that the revised collaboration remains admissible. Once either property is missing, cross-run improvement falls back to a blind search driven by the final score. For instance, on SWE-bench Verified~\citep{jimenez2024swebench}, a free-form multi-agent baseline reaches only $51.4\%$ File Match and an SOP-based baseline reaches $59.8\%$, far below the $86.2\%$ attained once the collaboration itself can be revised from execution traces (Table~\ref{tab:free_form}).

Existing collaboration representations hold only one of these two properties. \emph{Blueprint-driven} systems encode a graph, workflow, or standard operating procedure~\citep{hong2024metagptmetaprogrammingmultiagent,wu2023autogenenablingnextgenllm,fourney2024magenticonegeneralistmultiagentsolving}, and recent methods automate this design through workflow search or generated agent programs~\citep{zhang2025aflowautomatingagenticworkflow,hu2025automateddesignagenticsystems,zhang2025maasagenticsupernet}. Such designs are controllable, yet each selected workflow still determines the exact route taken during execution, and a runtime deviation therefore cannot be repaired locally. \emph{Agent-driven} systems let debate, dialogue, or dynamic connectivity emerge at runtime~\citep{li2023camelcommunicativeagentsmind,du2023improvingfactualityreasoninglanguage,liu2024dynamicllmpoweredagentnetwork,park2023generativeagentsinteractivesimulacra}, and a learned orchestrator can further reorder agent activations from reward~\citep{dang2025puppeteer}. Flexibility here costs transparency, since the realized coordination stays opaque and is hard to attribute or revise across runs. One line of work fixes the route and the other hides it, so neither yields a representation that is checkable at runtime and revisable from experience.

In this paper, we aim to make the collaboration pattern itself evolvable by holding flexibility and controllability in one representation. To this end, we introduce \emph{OpenAgency}, a self-evolving multi-agent system built on \emph{governed collaboration protocols}. As illustrated in Figure~\ref{fig:intro}, OpenAgency represents a protocol as a tuple $\mathcal{P}=(\mathcal{R},\mathcal{N},\alpha,\mathcal{H},\mu,\Omega,\mathcal{C})$ whose components fix the roles and the admissible handoffs between them. The admissible handoff set $\Gamma(n,s)$ carries both properties in a single object, since it rules out inadmissible transitions while the choice inside it is left to the agent at runtime. Because every coordination decision is expressed in this object and its legality is decidable, the collaboration pattern becomes revisable between runs. Building on this, OpenAgency records accepted handoffs, rejected handoffs, completion events, and failures in an immutable trace, and a collaboration-driven evolver turns this evidence into at most $k$ atomic edits over the protocol. A validity operator $\Pi_{\mathcal{V}}$ filters malformed candidates and an acceptance rule on a held-out subset deploys only revisions that do not regress, so every round stays admissible and traceable to the events that motivated it.

Experiments across fourteen benchmarks covering general question answering, long-horizon tasks, and production-oriented tasks show that OpenAgency achieves the best primary metric on every benchmark, lifting the unstructured multi-agent initialization by up to $54.6$ absolute points (Table~\ref{tab:main}). To the best of our knowledge, OpenAgency is the first multi-agent system in which the collaboration pattern is an evolvable object, updated from immutable execution traces without regenerating the whole workflow. We summarize our contributions as follows.
\begin{itemize}[leftmargin=1em, itemsep=-1ex, topsep=0ex]
    \item \textbf{Evolvable Collaboration Protocol:} We make the collaboration pattern itself a governed and evolvable object, because the admissible handoff set is checkable before a transition is taken and revisable after the run that produced it.
    \item \textbf{Collaboration-driven Evolution:} We propose an evolver that learns from the coordination evidence prior systems discard, namely rejected handoffs and failed completions, and converts it into at most $k$ atomic edits over protocol structure, predicates, and shared context. A validity operator and a held-out acceptance rule keep every deployed round admissible and free of regression.
    \item \textbf{Strong Performance:} OpenAgency reaches the best primary metric on all fourteen benchmarks (Section~\ref{sec:experiments}), and the same advantage holds against free-form and SOP collaboration substrates under an identical executor. Ablations further verify that both event content and temporal order are necessary for protocol evolution.
\end{itemize}

\section{Related Work}

\textbf{Multi-agent Collaboration.}\quad Existing systems expose collaboration with different degrees of structure. Blueprint-driven approaches encode graphs, workflows, or standard operating procedures~\citep{hong2024metagptmetaprogrammingmultiagent,qian2024chatdevcommunicativeagentssoftware,wu2023autogenenablingnextgenllm}. These systems make coordination explicit but typically fix the selected topology before execution. Agent-driven systems allow collaboration to emerge from debate~\citep{du2023improvingfactualityreasoninglanguage,liang2023encouragingdivergentthinking}, role-conditioned dialogue~\citep{li2023camelcommunicativeagentsmind,chan2023chateval}, or dynamic connectivity~\citep{liu2024dynamicllmpoweredagentnetwork,zhang2024chainagentslargelanguage}. Collaboration then adapts during execution, though the realized structure remains difficult to inspect and replay. Recent methods also optimize communication for accuracy or efficiency~\citep{sun2023corex,chen2024reconcileroundtableconferenceimproves,chen2024optima}. Across both families, the collaboration pattern is treated as a fixed design choice or as an emergent byproduct, and neither case leaves an object that later runs can update.

\textbf{Agent Self-evolution.}\quad Agent systems can improve through reasoning feedback, memory, prompt optimization, or program search. Reflexion and Self-Refine use rollout feedback to revise subsequent reasoning~\citep{shinn2023reflexion,madaan2023selfrefine}, while AgentGym and experiential co-learning accumulate experience across interactions~\citep{xi2024agentgym,qian2023experientialcolearning}. DSPy, TextGrad, and OPRO optimize language-model programs or prompt strings~\citep{khattab2024dspy,yuksekgonul2024textgrad,yang2024large}. More recently, AFlow, automated agent design, and MaaS search over workflow graphs or generated agent programs~\citep{zhang2025aflowautomatingagenticworkflow,hu2025automateddesignagenticsystems,zhang2025maasagenticsupernet}, while evolving orchestration trains a central controller to reorder agent activations~\citep{dang2025puppeteer}. These methods show that collaboration structure can be optimized, but what they return is an executable topology or a controller policy, neither of which exposes a boundary that a later round can check a candidate revision against.

In this work, we study which representation of collaboration can support evolution at all. OpenAgency defines a governed protocol that fixes admissible handoffs and completion conditions without prescribing one route through the graph. Agents therefore keep local choices during execution while every decision remains checkable, and this pairing is what makes the protocol revisable from immutable traces across runs. The difference from workflow search and orchestrator learning lies in the object being optimized. OpenAgency evolves the governance boundary that admits runtime decisions, while those methods optimize the executed route or the policy that produces it.

\section{OpenAgency}
\label{sec:method}

OpenAgency treats collaboration as a first-class object separated from the executors that realize each role. It combines a layered architecture (Section~\ref{sec:architecture}), a governed protocol that makes coordination inspectable (Section~\ref{sec:protocol}), and bounded protocol evolution driven by execution traces (Section~\ref{sec:self_evolving}). Figure~\ref{fig:intro} illustrates the overall pipeline.

\subsection{Multi-agent Architecture}
\label{sec:architecture}

To apply one collaboration protocol across different applications, OpenAgency must support heterogeneous executors without coupling the protocol to their backend-specific prompts and actions. To this end, OpenAgency separates multi-agent collaboration into three layers.

\textbf{Context Layer.}\quad The context layer maintains a shared collaboration space, such as a web console or an enterprise chat channel. Instructions, agent messages, human feedback, and coordination events are presented on a common timeline.

\textbf{Governance Layer.}\quad The governance layer hosts the collaboration protocol and validates each proposed handoff against the current protocol state. It records both accepted and rejected events in an immutable trace, providing the evidence used for later protocol evolution.

\textbf{Execution Layer.}\quad The execution layer binds each role to a concrete executor. An executor can be an LLM agent, a coding harness, a domain-specific tool, or a human reviewer. Executors sit below the governance layer, so the protocol constrains how roles hand off whichever backend realizes a role.

We formalize a running OpenAgency instance at step $t$ as
\begin{gather}
    \mathcal{I}^{(t)} = (\mathcal{X}^{(t)}, \mathcal{P}, \mathcal{E}, s^{(t)}),
\end{gather}
where $\mathcal{X}^{(t)}$ is the shared context, $\mathcal{P}$ is the governed protocol, $\mathcal{E}$ is the set of available executors, and $s^{(t)}$ is the current protocol state. The map $\rho: \mathcal{R}\rightarrow\mathcal{E}$ binds each role in the role set $\mathcal{R}$ to an executor and is separate from the protocol logic.

Given this architecture, the governance layer renders the shared state into a role-specific execution context, since an LLM executor may require tool instructions and structured commands while a human executor may require a concise protocol description. We write this rendering as
\begin{gather}
    u^{(t)} = f_{\mathrm{ctx}}\bigl(\mathcal{X}^{(t)}, s^{(t)}, n, r, \mathcal{P}\bigr),
\end{gather}
where $n$ is the active node and $r$ is its assigned role. Executor adapters produce $u^{(t)}$ and return messages, handoffs, finishes, and failures in a common event representation, so the executor bound to a role can change without changing the handoff rules, trace format, or completion predicates.

\subsection{Governed Collaboration Protocols}
\label{sec:protocol}

To govern collaboration without fixing a complete execution route, the protocol must expose enough structure to validate each handoff while preserving the agent's choice among admissible targets. OpenAgency therefore represents collaboration as a declarative tuple, which decouples validation, coordination, and local decision while keeping one shared description.

\textbf{Protocol Definition.}\quad OpenAgency represents a governed collaboration protocol as
\begin{gather}
    \mathcal{P} = (\mathcal{R},\, \mathcal{N},\, \alpha,\, \mathcal{H},\, \mu,\, \Omega,\, \mathcal{C}),
\end{gather}
where $\mathcal{R}$ is the set of roles, $\mathcal{N}$ the set of collaboration nodes, $\alpha\colon \mathcal{N}\to\mathcal{R}$ assigns each node to a role, $\mathcal{H}\subseteq\mathcal{N}\times\mathcal{N}$ defines admissible handoff edges, $\mu(n)\in\{\texttt{ONE},\texttt{SOME},\texttt{ALL}\}$ is the handoff mode, $\Omega_n$ is the completion predicate, and $\mathcal{C}$ contains the shared \texttt{rule} and \texttt{culture} that every role sees.

\textbf{Admissible Handoff Set.}\quad For a node $n$ under state $s$, the admissible handoff set is
\begin{gather}
    \Gamma(n,s) = \bigl\{\, n' \in \mathcal{N} \;\bigm|\; (n,n') \in \mathcal{H} \text{ and the transition is valid under } s \,\bigr\}.
\end{gather}
The handoff mode $\mu(n)$ then determines how the active agent selects targets from $\Gamma(n,s)$. Under \texttt{ONE}, the agent picks exactly one admissible target. Under \texttt{SOME}, the agent picks a nonempty subset. Under \texttt{ALL}, the agent activates all admissible targets. A node with no admissible target completes without a handoff, and the local choice within $\Gamma(n,s)$ is left to the agent.

\textbf{Handoff Validation and Completion.}\quad When the agent proposes a handoff $(n,B,m)$ with target set $B$ and message $m$, the protocol validates whether $B$ is admissible under $\mu(n)$. An admissible handoff commits $B$ as pending targets and updates the state, and an inadmissible handoff leaves the state unchanged and returns structured feedback so the agent may propose another target. Committing a target set does not immediately activate it. A finish event $(n,y)$ confirms that the source node has completed its work, after which the governance layer activates the committed targets only when $\Omega_n(y)$ holds. Downstream execution therefore waits for the completion predicate even after the agent has committed an admissible target set.

\begin{algorithm}[t]
\footnotesize
\caption{Collaboration under a Governed Protocol}
\label{alg:protocol}
\begin{algorithmic}[1]
\renewcommand{\algorithmicrequire}{\textbf{Input:}}
\Require Protocol $\mathcal{P}$, initial context $\mathcal{X}$, executor mapping $\rho\colon\mathcal{R}\to\mathcal{E}$
\renewcommand{\algorithmicrequire}{\textbf{Output:}}
\Require Immutable collaboration trace $\tau$

\State $\tau \gets \emptyset$; activate start node $n_0$; obtain initial state $s$
\While{active nodes exist}
    \For{each active node $n$ with role $r = \alpha(n)$}
        \State $e \gets \rho(r)\bigl(f_{\mathrm{ctx}}(\mathcal{X}, s, n, r, \mathcal{P})\bigr)$ \Comment{executor proposes an event}
        \If{$e$ is a handoff $(n, B, m)$ and $B$ is admissible}
            \State commit $B$, update $s$, append $(e, s)$ to $\tau$
        \ElsIf{$e$ is a handoff}
            \State append $(e, s)$ to $\tau$; return structured feedback to $\rho(r)$
        \ElsIf{$e$ is a finish $(n, y)$ and $\Omega_n(y)$ holds}
            \State mark $n$ complete; activate committed targets; append $(e, s)$ to $\tau$
        \Else
            \State append $(e, s)$ to $\tau$
        \EndIf
    \EndFor
\EndWhile
\State \Return $\tau$
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:protocol} summarizes the runtime interpreter. It updates the state only for admissible handoffs and valid completions, while retaining every event in the trace so that later evolution can use both successful and unsuccessful coordination.

\subsection{Collaboration-driven Protocol Evolution}
\label{sec:self_evolving}

Given a protocol whose decisions are explicit and checkable, the remaining question is how to revise it from experience. A single run records many local coordination events while the final answer alone cannot indicate which of them should change, and regenerating the whole workflow each round would destroy the governance boundary that makes a change inspectable. OpenAgency addresses both by keeping the coordination evidence that prior systems discard and by restricting each round to a few validity-checked atomic edits.

\textbf{Immutable Collaboration Trace.}\quad Each execution produces an ordered trace $\tau=(e_1,s_1),\ldots,(e_T,s_T)$ of coordination events with the resulting states, where an event $e_t$ is one of accepted handoff, rejected handoff, finish, message, or failure. Unlike prior systems that keep only the successful trajectory or the final score, the trace retains rejected handoffs and failed completions, which record the transitions the collaboration attempted and could not take. This counterfactual evidence tells the evolver where the boundary was drawn in the wrong place and is not recoverable from the final answer alone.

\textbf{Bounded Edit Proposer.}\quad At round $v$, an LLM proposer $f_{\mathrm{evolve}}$ receives the current protocol together with a summary of recent traces and run-level quality signals, and returns a composite edit that contains at most $k$ atomic changes:
\begin{gather}
    \hat{\mathcal{P}}^{(v+1)} = f_{\mathrm{evolve}}\bigl(\mathcal{P}^{(v)},\, \tau^{(1{:}v)},\, q^{(1{:}v)}\bigr), \qquad |\hat{\mathcal{P}}^{(v+1)}\ominus\mathcal{P}^{(v)}|\le k.
\end{gather}
The edit space covers three levels. \emph{Structural} edits add or remove nodes and handoff edges, reassign roles, or change handoff modes. \emph{Predicate} edits modify transition and completion predicates. \emph{Contextual} edits rewrite the shared \texttt{rule} and \texttt{culture}. We set $k=4$, which keeps each candidate a small, inspectable change and avoids regenerating the whole workflow.

\textbf{Validity Operator and Acceptance Rule.}\quad Each candidate first passes a structural validity check $\Pi_{\mathcal{V}}$ that rejects malformed handoff edges, unresolved role references, and unreachable completion states. Writing $\tilde{\mathcal{P}}^{(v+1)} = \Pi_{\mathcal{V}}\bigl(\hat{\mathcal{P}}^{(v+1)}\bigr)$ for the validity-checked candidate, the acceptance rule is
\begin{gather}
    \mathcal{P}^{(v+1)} =
    \begin{cases}
        \tilde{\mathcal{P}}^{(v+1)}, & \tilde{\mathcal{P}}^{(v+1)} \neq \bot \;\land\; q_{\mathrm{sel}}\bigl(\tilde{\mathcal{P}}^{(v+1)}\bigr) \ge q_{\mathrm{sel}}\bigl(\mathcal{P}^{(v)}\bigr),\\[2pt]
        \mathcal{P}^{(v)}, & \text{otherwise},
    \end{cases}
\end{gather}
where $q_{\mathrm{sel}}$ is the primary metric measured on a held-out selection subset disjoint from the evaluation set. A candidate is deployed only when it passes the validity check and does not regress on that subset, thereby binding every deployed round to the collaboration trace that produced it.

\section{Experiments}
\label{sec:experiments}

We evaluate the governed protocol of Section~\ref{sec:method} on fourteen benchmarks (Section~\ref{sec:benchmarks}) under one executor and tool budget (Section~\ref{sec:setup}), report the main comparison in Section~\ref{sec:main_results}, and analyze in Section~\ref{sec:analysis} where the gain comes from, covering the round-wise effect of protocol evolution (Section~\ref{sec:evolution_effect}), the advantage of multi-agent protocols (Section~\ref{sec:ablation_multi}), the trace signal the evolver consumes (Section~\ref{sec:ablation_evolve}), the comparison against free-form and SOP substrates (Section~\ref{sec:free_form}), and the activity of the governance boundary (Section~\ref{sec:admissible}).

\subsection{Benchmarks}
\label{sec:benchmarks}

We evaluate OpenAgency on fourteen benchmarks organized into three categories. \emph{General question answering} contains HumanEval~\citep{chen2021humaneval}, MBPP~\citep{austin2021mbpp}, GSM8K~\citep{cobbe2021gsm8k}, MATH~\citep{hendrycks2021math}, and HotpotQA~\citep{yang2018hotpotqa}, and stresses whether protocol adaptation helps when each instance admits a short answer. \emph{Long-horizon tasks} contains SWE-bench Verified~\citep{jimenez2024swebench}, DeepPlanning~\citep{zhang2026deepplanning}, and the text-only subset of Humanity's Last Exam (HLE)~\citep{phan2025hle}, and stresses whether governed handoffs support dependent decisions. \emph{Production-oriented tasks} contains DevEval~\citep{li2024deveval}, DDR-Bench~\citep{liu2026ddrbench}, TheAgentCompany~\citep{xu2024theagentcompany}, MARBLE~\citep{zhu2025marble}, AutomationBench~\citep{shepard2026automationbench}, and OfficeQA Pro~\citep{opsahlong2026officeqa}, and stresses whether one protocol representation applies across heterogeneous tools and task surfaces. Appendix~\ref{app:benchmarks} describes each benchmark.

\subsection{Experimental Setup}
\label{sec:setup}

Governed collaboration and its evolution have to be separated from the executor's own capability, so we use GPT-5.5 as the underlying language model across all benchmarks, and each role receives the tool surface its benchmark requires. For each benchmark, we compare three in-house conditions under an identical model and tool budget, namely a single-agent ablation with one role and no handoff, the unstructured multi-agent initialization $v_0$, and the evolved protocol after four rounds ($v_4$). We report all three against a prior reference (Prior Ref.), a strong baseline from prior work that fixes the absolute level of the benchmark. The prior reference is a same-model direct-LLM baseline when the benchmark's authors report no stronger external system, and the strongest externally reported model or agent otherwise. Model, temperature, and tool budget stay fixed across rounds, and only the protocol template changes. Table~\ref{tab:main} reports the final round and Appendix~\ref{app:detail} lists all four rounds.

\textbf{Capability on General Question Answering.}\quad The five single-turn benchmarks (HumanEval, MBPP, GSM8K, MATH, HotpotQA) probe \emph{short-chain reasoning capabilities}, since each instance admits a single well-defined answer and leaves little room to coordinate. Under a common GPT-5.5 executor, we compare OpenAgency with the single-agent ablation, the unstructured multi-agent initialization, and each benchmark's strongest prior reference. As shown in Table~\ref{tab:main} and summarized across the three categories in Figure~\ref{fig:main_radar}, OpenAgency obtains the best primary metric on all five benchmarks, reaching $100.0$ pass@1 on HumanEval and lifting MATH from $32.4$ to $87.0$ over the initialization. Agent count alone does not produce this gain, since the unstructured initialization trails the single-agent ablation on HotpotQA at $64.0$ against $75.9$ F1 while the governed protocol carries the same benchmark to $82.3$. Evolution prunes handoffs whose upstream output the trace repeatedly flags as ineffective, and each benchmark settles on a tight solve-critique-revise loop matched to its dominant failure mode. On HotpotQA the admissible set further rejects the collapsing edges that free-form communication produces once a single answer has to be preserved, so the protocol turns a short chain into a verified one.


\textbf{Capability on Long-horizon Tasks.}\quad SWE-bench Verified, DeepPlanning, and HLE stress \emph{long-horizon reasoning capabilities}, since each instance requires several dependent decisions and a bad handoff at any stage can invalidate the entire run. We compare OpenAgency with a monolithic single-agent solver and each benchmark's strongest prior reference. Table~\ref{tab:main} reports a lead on all three, reaching $86.2$ File Match on SWE-bench Verified against a prior reference of $42.8$ and $37.7$ accuracy on HLE against $18.0$. What produces the lead is visible in the protocol each benchmark converges to. On SWE-bench the evolver installs a retry edge when a patch fails and splits an overloaded Verifier into structural and semantic components. The DeepPlanning protocol hands a dedicated Verifier the user-specified constraints one at a time under the validity operator, turning a brittle end-to-end plan into a chain of locally verifiable handoffs. Verification on HLE becomes conditional, routing high-confidence answers straight to completion and sending refused or low-confidence ones back through a retry edge, which concentrates effort on the questions that need another pass. All three shapes are reached from the same initialization, so it is the handoff and completion rules that adapt when local errors are unrecoverable.




\textbf{Capability on Production-oriented Tasks.}\quad The six production-oriented benchmarks (DevEval, DDR-Bench, TheAgentCompany, MARBLE, AutomationBench, OfficeQA Pro) test \emph{cross-domain deployment capabilities}, since each exposes a different tool surface and task format. Measured against each benchmark's strongest prior reference and against its own ablations, OpenAgency leads on all six in Table~\ref{tab:main}, improving over that reference by $34.4$ points on DevEval, $19.6$ points on MARBLE, and $12.8$ points on OfficeQA Pro. The template behind these numbers is read off the immutable trace and differs per benchmark, from a Reader-Solver-Verifier chain on OfficeQA Pro to a Generator-Critic-Reviser pipeline on MARBLE. Two cases expose what the governance layer contributes. On DDR-Bench, an Auditor role introduced during evolution forces every quantitative finding in the trace to be reflected in the final report, fixing a class of silent omission that free-form multi-agent baselines leave undetected. The admissible-set constraint on MARBLE keeps each handoff terminating under a protocol that would otherwise allow any-to-any messaging. In both cases the governance layer supplies a constraint the task format alone does not, and it does so without a protocol-level rewrite.







\section{Analysis}
\label{sec:analysis}

\subsection{Effectiveness of Protocol Evolution}
\label{sec:evolution_effect}

To verify that bounded protocol edits keep improving collaboration after the first revision, we track the primary metric from the unstructured multi-agent initialization $v_0$ to the evolved rounds $v_1$ through $v_4$ on all fourteen benchmarks. As shown in Figure~\ref{fig:evolution} and Table~\ref{tab:evolution_all}, the evolved protocol improves the primary metric over the initialization on every benchmark, and the gain is not confined to one task category, reaching $54.6$ points on MATH and $48.9$ points on MARBLE. The round-to-round trajectory is non-decreasing on every benchmark, which is the behavior the held-out acceptance rule is designed to enforce on bounded edits. Collaboration-driven revision therefore keeps improving the governed protocol after the first round.

\subsection{Advantage of Multi-agent Protocols}
\label{sec:ablation_multi}

OpenAgency attributes its gain to governed collaboration, while a multi-agent system can also improve through sheer agent count. To separate the two, we compare OpenAgency with its single-agent ablation under an identical GPT-5.5 executor and tool surface. As shown in Figure~\ref{fig:svm}, OpenAgency exceeds the single-agent ablation on every benchmark, with the widest gaps on MATH, OfficeQA Pro, and DevEval. A single node has to interleave solving and checking inside one context, while the governed protocol makes that separation explicit, either by routing a partial output to a downstream role whose completion predicate validates it independently, or by tightening a solver's internal phases when the trace shows that a separate role adds no evidence. Read together with the unstructured-initialization column of Table~\ref{tab:main}, the results confirm that the multi-agent gain traces to the protocol design, since the unstructured initialization does not reach the same level under the same agent budget.

\subsection{Comparison against Free-form and SOP Baselines}

The free-form baseline is the weakest everywhere, and the SOP baselines recover part of the gap because the collaboration order is enforced, yet their procedure is fixed at design time and cannot absorb trace-level failure signals. OpenAgency governs collaboration through the admissible handoff set $\Gamma(n,s)$, whose activity during execution determines how much of the collaboration structure is actually enforced. To verify that the boundary is active during execution, we measure how often $\Gamma(n,s)$ refuses a handoff an agent proposes. On the four benchmarks of Section~\ref{sec:free_form} we log every proposed handoff during the $v_4$ runs, record the fraction $\Gamma(n,s)$ refuses, and count the runs whose outcome changes once the refusal redirects the handoff to an admissible target. As shown in Table~\ref{tab:handoff}, the boundary refuses $3.8\%$ to $8.2\%$ of proposed handoffs and changes the outcome of $2.9\%$ to $5.3\%$ of runs. Refusals are most frequent on TheAgentCompany, whose heterogeneous tool surface offers the most chances to address a collaborator that cannot serve the current state, and least frequent on the near-linear DDR-Bench pipeline. Overall, the boundary stays active on all four benchmarks, and its benefit comes from ruling out the wrong collaborator at the points where it matters while leaving the common path unconstrained, and these refused events are the evidence the evolver consumes in Section~\ref{sec:self_evolving}.

\section{Conclusion}

In this paper, we introduce OpenAgency, a self-evolving multi-agent system based on governed collaboration protocols. By constraining runtime handoffs while preserving each agent's choice among admissible collaborators, OpenAgency makes the collaboration pattern an evolvable object, and it turns ordered traces, including the rejected handoffs that prior systems discard, into bounded protocol updates filtered by a validity operator. Experiments on fourteen benchmarks show that OpenAgency achieves the best primary metric on every benchmark, outperforming the strongest prior reference and its own single-agent and unstructured multi-agent ablations.

\section{Case Study of Protocol Evolution}
\label{app:case_study}

Figure~\ref{fig:case_evo} shows how the protocol evolves across rounds on the nine long-horizon and production-oriented benchmarks, which jointly cover repository-level coding, planning, retrieval, workflow orchestration, and open-ended research. On every benchmark the number of nodes remains small ($\leq 4$ across rounds), so evolution acts as a rewiring process over a protocol that stays small across very different task surfaces.

The three edit levels are unevenly used. Structural edits dominate, appearing in $22$ of the $27$ revisions in Figure~\ref{fig:case_evo}, and the remaining five revise a predicate or the shared context without touching the graph. DevEval is the clearest case, where the second round moves unit-test injection into the shared rule and the third round bounds the review loop and records known error patterns, both without adding a role. Both rounds change how the protocol behaves while leaving the graph fixed, which a static topology has no place to record.

On the coding and planning benchmarks, evolution mainly redistributes verification responsibility. The SWE-bench protocol first attaches a retry edge from the Verifier back to the Editor, then re-routes the Verifier back to the Locator, and finally splits the Verifier into structural and semantic components. DevEval gains a self-test node between the Coder and the Reviewer. DeepPlanning grows from a monolithic solver into a Researcher-Solver-Verifier chain with an explicit constraint checklist.

On the retrieval and research benchmarks, evolution adds evidence-preserving roles. The DDR-Bench protocol fixes the Researcher-to-Reporter handoff to forward the raw evidence set, splits a single reporting phase into two, and installs a quantitative Auditor. OfficeQA Pro converts a monolithic solver into a Reader-Solver-Verifier chain over an external document store. MARBLE replaces the initial Reviewer-Brainstormer-Writer handoff with a compact Generator-Critic-Reviser pipeline and adds a feasibility-driven retry edge from the Critic back to the Generator.

Evolution also shrinks the graph when coordination is unnecessary. AutomationBench collapses a two-node Executor-Verifier pipeline into a single-node solver with progressively tightened internal phases, while HLE grows a confidence-routed subgraph that skips verification on high-confidence answers and adds a retry edge on refused ones. Appendix~\ref{app:extra} reports the compute budget these revisions consume, the candidate edits the acceptance rule refused, and the component measurement on which the accepted edits pay off.

Every admitted candidate attaches or tightens a duty that can be checked, from an extra repair round to a structural verification step to self-verification before handoff. The rule therefore admits obligations and refuses material, and a system that took every proposal would have carried the $75.0$ candidate forward as its incumbent.
